227 AI / Get Started

From Tools to your first chat.

Install once with an internet connection. Then ask, dictate and listen locally, with no cloud account and no connection required for everyday use.

R36S / dArkOSREManager 1.2.0Checked against current source

Before you start

These instructions are tested on an R36S running dArkOSRE. You need an internet connection for installation and about 700 MB of free space on your SD card. The easy method uses a computer and an SD card reader. Other ArkOS-style firmware may work, but has not been verified on every handheld. See the tested setup.

Keep the handheld powered during installation. Back up any existing conversations before updating or reinstalling.

Technical requirements and SD card details
  • A writable SD card actually mounted at /roms or /roms2. An empty directory with that name is not sufficient.
  • Approximately 650 MiB of free space on a fresh app destination for downloads, extraction, staging and headroom; about 25 MiB of additional staging space when the installed runtime and both models verify. These are budgets, not exact install sizes. Retained partials also reduce the budget. System packages need separate space on the system partition.
  • Python 3.9 or newer, curl, system SDL2 and SDL2_ttf libraries for the graphical manager. The bootstrap can set up missing capabilities on supported firmware; an existing broken or older Python fails without upgrade. Regular/bold DejaVu Sans Mono fonts are bundled on the card, not a manual OS-font requirement.
  • Internet access for the initial downloads, unless you supply a complete local bundle.
  • For the app: libespeak-ng.so.1 and usable English voice data, ALSA arecord/aplay/amixer, and procps pkill. The core checks these after confirmed install/update. Dictation additionally needs a usable USB microphone.

Keep the handheld powered and back up any existing conversations before maintenance. The installer changes the selected card's application files and the shared EmulationStation configuration; it does not restart EmulationStation for you.

Two cards, two separate choices. The bootstrap chooses a Tools card to store the manager. You then explicitly select the app's destination inside the manager. These can be different cards, regardless of where your games are stored.

Installation

Easy Install (No Commands Needed)

  1. Copy the installer to your SD card. On your computer, download install227ai.sh. Turn off the handheld, put the SD card you use for games into your computer, and copy the downloaded file into its tools folder (alongside the game folders, not inside one). Safely eject the card and put it back in the handheld.
  2. Connect to Wi-Fi, install, then restart. Turn on the handheld and connect it to Wi-Fi. In the game menu, open Tools and select install227ai (it may be shown as install227ai.sh). On the installer screen, use the D-Pad and A to select the card you want to install on: Main SD / SD1 or Second SD / SD2. Choose INSTALL, confirm Yes, and wait for success. Only then restart the handheld. Open 227 > 227 AI to start chatting.

Keep the handheld powered while it installs. Wi-Fi is needed for the downloads; once installed, 227 AI works offline. You do not need SSH or terminal commands for this method. If you cannot see the card's game folders or tools folder on your computer, do not format the card; use the SSH method below instead.

Advanced Install (SSH)

Use this method if you already have SSH enabled on the handheld and want to download the installer without removing the SD card. Connect from a terminal on your computer, replacing the placeholders with your handheld's username and IP address. Run the remaining commands in that SSH session, in the card's existing tools folder.

Connect from your computer
ssh YOUR_USER@YOUR_HANDHELD_IP
Choose the mounted Tools folder for these commands

The commands default to SD1. The selector changes both blocks together; you still choose the app destination separately inside the manager.

On the handheld: download, then inspect
cd /roms/tools && \
curl -fL --connect-timeout 15 --max-time 120 -o install227ai.sh.download \
  https://github.com/1Z99/project-ai-r36s/releases/download/v1.0.0/install227ai.sh && \
mv install227ai.sh.download install227ai.sh && less install227ai.sh

Stop if any command fails. Do not launch an older file after a failed download. After a successful download, read the script in the viewer and press q to close it. If less is not installed, open the downloaded file in a text editor before continuing. There is no need to pipe a remote script straight into a shell.

On the handheld: launch after successful review
sh /roms/tools/install227ai.sh

The installer opens on the handheld's screen, not in your SSH terminal. Use the D-Pad and A to choose Main SD / SD1 or Second SD / SD2, choose INSTALL, confirm Yes, and wait for success. Only then restart the handheld and open 227 > 227 AI. The install card you choose on screen can be different from the card holding the downloaded file.

Installer details

The release asset is a bootstrap for current code, not a frozen v1.0.0 app bundle. The bootstrap downloads four matching manager modules from repository main: UI, core, CLI and installer_deps.py. If any is missing, it refreshes the whole set, checks for nonempty valid Python, then publishes with per-file renames. A complete stored set is reused. Syntax validation is not a cryptographic authenticity check. The core resolves online app source to an immutable main commit before staging. Review the download trust boundaries for local installs.

Automatic dependencies

The shell validates installed Python 3.9+ before running Python and can install absent Python or curl. It never upgrades or replaces an existing broken/old Python. Before the graphical manager opens its SDL display, the helper checks manager SDL libraries and curl. Only after you explicitly confirm install/update does the core check all app dependencies, including eSpeak English data, ALSA tools and procps. If everything works, these checks make no APT/package-database queries and no system changes.

Only absent capabilities trigger automatic package setup. It requires Debian/Ubuntu-family firmware, aarch64, dpkg architecture arm64, APT, and root or noninteractive sudo -n. No password is requested or stored. Unsupported systems or denied administrator access produce a clear error and missing-package list. This is not support for arbitrary Linux systems or a guarantee for all firmware.

APT simulates with --no-upgrade --no-remove --no-install-recommends, pins the full dependency closure and verifies the plan again before installing. It rejects upgrades, removals and protected graphics/firmware packages, including Mesa/EGL/GLES/GBM/DRM/Mali. Package indexes refresh only if the initial simulation fails. Broken existing libraries are errors, not permission to replace a working graphics stack.

The bootstrap SHA-256-validates regular/bold fonts and their existing DejaVu license in the manager's fonts/ directory. Manager and app use bundled fonts without requiring OS fonts; app copies live in its data root, with OS fonts as fallback. Desktop, help, dry-run and uninstall skip automatic dependency setup. Shared system packages use the system partition, are outside app-file rollback and the SD staging budget, and remain installed after app removal.

Choose a card

The manager detects Main SD / SD1 at /roms and Second SD / SD2 at /roms2 independently. Both mounted, writable cards are eligible app destinations, even if EmulationStation currently uses only one for ROMs. Unmounted or read-only cards display a reason and cannot be selected.

Use D-Pad Left/Right to move between card choices and A to select one. Up/Down moves through the card/action rows. Choose the desired action with A, then move the confirmation to Yes and confirm again. X refreshes card discovery on the home screen and clears the previous selection.

The manager remains on its original Tools card. Bootstrap storage prefers the card containing the launcher; otherwise it tries writable, mounted /roms2, then /roms. This fallback never silently chooses where the app is installed.

Installing on the other card does not move or delete the first copy. EmulationStation has one shared 227 registration. A new install on another card repoints it there. Back up and maintain each copy deliberately; the card picker is not a migration tool.

First launch

Open 227 > 227 AI after refreshing EmulationStation. The opening animation is optional, and the local model must load before the engine reports READY. Startup and first-answer work can take time on this hardware; there is no documented speed guarantee.

  1. Press A to open the keyboard when the pointer is not highlighting an existing reply's read-aloud target.
  2. Move between keys with the D-Pad and type with A. Use Y for a space and B to delete. Up from the top keyboard row selects available word suggestions.
  3. Press X or activate SEND. Ask one short, concrete question to begin.
  4. Scroll with D-Pad Up/Down. Open history with X, start a new chat with Y, or open Settings with R2.

To dictate, select the keyboard's MIC key, speak, and activate it again to stop. Recording stops automatically at 30 seconds. Wait for local English transcription, check the resulting draft, then send it yourself. To read a reply aloud, move the pointer over the reply and press A; press A again to stop playback.

Text chat does not require a microphone. For voice setup, open R2 > VOICE, select your microphone/speaker device and run TEST MICROPHONE. See Speech and microphone setup for the complete flow and limits.

The deployment manager

Reopen Tools > Install 227 AI for maintenance. Its self-locating launcher starts the stored manager directly; SSH and terminal input are not needed. Select the app card again every time.

The 227-ai-manager/ folder holds support files, not another tool to open. Its internal launcher is named install.bootstrap, so EmulationStation's recursive .sh scan does not list the folder in Tools. Keep the folder in place; the normal Tools shortcut needs it.

Seeing the manager folder in Tools?

You have an older bootstrap. Download and inspect the updated install227ai.sh, then run it once from the same Tools card as your existing manager. It publishes the replacement bootstrap and shortcut before removing the legacy internal install.sh. Close the manager and restart EmulationStation to clear the old folder entry. No app reinstall or manual folder deletion is needed.

Manager actions and controls
Action or controlWhat happens
INSTALLStages application files, verified binaries and models, then publishes the launcher and system registration. Existing settings and conversations are preserved.
UPDATE / REPAIRCompares source contents and verifies installed files. Reports an actual no-op or repairs missing/changed items, using the same preservation rules as install.
UNINSTALLDeletes the selected card's app and data after confirmation. Keeps the independent manager.
B during workOpens a cancellation confirmation. Partials remain for retry; finalization cannot safely stop midway.
A / X / B after failureRetry or resume / inspect details / return to the menu.

Progress describes the current file or task, not an invented whole-install percentage. Transferred bytes, rate, elapsed time and a file ETA appear when available. A server that does not report a length produces indeterminate progress.

Do not power off during system setup or finalization. A cancellation request waits for running APT installation to finish before taking effect, just as publication, rollback or destructive removal cannot safely stop midway. App-file rollback does not undo installed system dependencies and is not power-loss recovery. If restoration fails, the error reports retained backup locations.

Updates and repair

Exit 227 AI, back up your data, connect to the internet if required, and open the manager. Select the installed app's card, choose UPDATE / REPAIR, confirm, and wait for success. Restart EmulationStation if its registration or artwork needs refreshing.

Existing config.json, chats.json and history.json are preserved. The local backend returns up_to_date and the manager shows YOU'RE UP TO DATE only after managed source files, actual model/runtime hashes, owned ES/theme metadata, required executable permissions and config-file existence all check out. It skips app-file writes, not downloads, staging, cache or logs. ES play statistics and unrelated metadata are preserved; harmless XML rewrites do not count as updates.

Missing/invalid models or runtime, launchers, permissions and menu registration trigger repair. Differing existing payload bytes are reported as Updated/repaired files: without a recorded release baseline, the check cannot reliably distinguish corruption from a newer version. It does not invent a version baseline. A local --source or bundle/ compares that local tree, not GitHub; the UI explicitly labels a local test bundle.

An online check needs internet even when nothing changed. The core resolves GitHub main through the API, then stages app/assets/licenses/system files from that immutable commit. API rate limits, network errors or source-fetch failures report that it cannot check, never a cached up-to-date success. Cached downloads are not evidence of fresh source.

App source and binary releases are different channels. Binary URLs use releases/latest/download, with runtime and model hashes pinned by the manager core. The documented runtime release is v1.0.0; that tag does not freeze current app source. The bootstrap and manager report version 1.2.0.

Update / Repair does not update the manager. A complete set of four stored modules is reused. Manager updates remain a separate manual maintenance task involving the bootstrap and matching UI, core, CLI and dependency-helper modules. A missing module refreshes the whole set with the new bootstrap, but this is not a one-button manager self-update. Consult release instructions rather than deleting a module to force an improvised update.

The Tools-menu cleanup only needs the updated public bootstrap run once. It updates the retained launcher and removes the duplicate internal menu entry; a complete set of cached Python manager modules is still reused.

Sharing 227 with TV or other apps? Some AI manager versions replace the whole game list or remove the shared menu on uninstall. Back up the menu and verify your manager backend before AI maintenance; downloading a new bootstrap alone does not replace a complete cached backend. The website update does not change installer behavior. If TV's entry is lost, close TV and use Repair in the TV manager.

Uninstall

Uninstall permanently removes conversations. It deletes app code, models, runtime, settings, chats, history, artwork and cache on the selected card. Make your backup first.

Exit the app. Open Tools > Install 227 AI, explicitly choose the card to remove, select UNINSTALL, and confirm. Wait until removal finishes before rebooting or removing a card.

The manager directory and Install 227 AI Tools entry remain so you can reinstall. Only a 227 system registration pointing into the selected card is removed; unrelated EmulationStation systems and a registration pointing at the other card are preserved. The installer does not restore a legacy whole-config backup. Restart EmulationStation to refresh its system list.

Shared OS dependencies are kept. Uninstall does not run automatic dependency setup or remove system packages.

Back up your conversations

Close 227 AI before copying files, so you do not race a save. Under the installed card's tools/project_ai/, copy config.json, chats.json and history.json to storage outside the managed app and cache directories. Files appear as they are needed, so a fresh install may not have all three.

chats.json holds saved conversations; history.json holds the recent session; config.json holds preferences, including your custom system prompt once saved. Keeping all three is safer than treating recent history as a complete archive. For a full snapshot, copy the whole data directory, allowing for the much larger models and runtime.

To restore, install the app on the intended card, keep it closed, and copy the saved JSON files back into that card's data directory. Preserve an untouched copy of the backup. There is no built-in cloud sync, backup scheduler, or import wizard. These are unencrypted local files; protect the backup accordingly.

Headless CLI

CLI mode is explicit and uses the same backend as the graphical manager. Every modifying action requires --cli, an explicit --roms destination, an action and --yes. Run these from the directory containing the bootstrap; substitute /roms2 only when that is your intended mounted app card.

Help and install
sh install227ai.sh --help
sh install227ai.sh --cli --roms /roms --action install --yes
Preserving update
sh install227ai.sh --cli --roms /roms --action update --yes

The following command is destructive, including settings and conversations:

Remove the selected card's app
sh install227ai.sh --cli --roms /roms --action uninstall --yes

What dry-run actually checks

Read-only target validation
sh install227ai.sh --cli --roms /roms --action install --dry-run

Dry-run discovers cards and validates the target without network access or writes: no manager download, log, lock, cache or bytecode creation. It needs an existing installer_core.py beside the bootstrap or in installer/. A fresh standalone bootstrap therefore refuses dry-run rather than downloading its dependencies. It does not test transfers or calculate staging-space requirements. --help also avoids SDL, network and writes.

Do not pass CLI action flags to graphical mode. For isolated paths and source builds, see Local builds.

Troubleshooting

There is a second installer inside a manager folder

That is the old internal launcher, not a separate installer. Follow the Tools-menu cleanup instructions to migrate it safely. Use Tools > Install 227 AI afterward; do not delete the manager's support folder.

The manager closes before a window appears

Inspect <Tools card>/tools/227-ai-manager/bootstrap.log for Python, SDL or bundled-font validation errors. The bootstrap reports missing packages or unsupported/no-admin setup; an existing broken/old Python needs manual repair, not automatic upgrade. Bootstrap failures try an optional dialog message box, but if SDL cannot start and there is no usable console, a persistent graphical error is unavailable. Before manager storage exists, errors may only reach stderr or an available dialog. Fix the dependency or network error and relaunch.

My card is unavailable

Check that it is actually mounted at /roms or /roms2, writable, and not redirected by a symlink. Read the displayed reason. Do not create a plain directory to imitate an absent card or force a read-only card writable without investigating. Refresh discovery with X.

A download failed or seems stuck

Check Wi-Fi and the error details with X; press A to retry/resume. Transfers have connection, low-speed and overall timeouts. Models try the release mirror before Hugging Face. Retained partials can be reused, but a source that refuses range requests may restart. Manager events are in 227-ai-manager/installer.log; CLI events are in installer-cli.log. Do not bypass a checksum mismatch.

The update check cannot verify GitHub main

Check internet access and the error details, including GitHub API rate limits, then retry. A source/API failure is not a successful no-op, and cache cannot prove the source is current. Local-bundle checks only compare that bundle and are labeled as local.

The 227 system is missing

Restart EmulationStation or reboot after a completed install. If it still does not appear, select the correct card and run Update / Repair. The shared /etc/emulationstation/es_systems.cfg should contain a <name>227</name> entry pointing at that card's 227ai/ directory.

The engine does not become ready

Allow time for model loading. If it reports an error, use the installed LFM model and the default 768-token context, check free memory, and repair missing runtime/model files. Engine diagnostics are in /tmp/project_ai_server.log. A model profile's presence is not proof it fits available memory.

Dictation or read-aloud is unavailable

Use a USB microphone, check ALSA tools, and run R2 > VOICE > TEST MICROPHONE. Read-aloud needs the system libespeak-ng.so.1. See speech dependencies and diagnostics. There is no separate MIC TEST application to launch.

Still blocked? File an issue with firmware, selected card, action, exact error and relevant log excerpts. Review logs for private text before sharing them.
