Architecture

The application is a Python controller-first client using system SDL libraries through ctypes. It resolves project_ai/ beside its own file, so its paths are not hard-coded to SD1 or SD2. A separate settings module shares rendering primitives and delegates persistence and engine changes back to the host app.

The local engine starts the bundled llama-server as a child process with a private library path. The server binds 127.0.0.1:39227 with offline mode, no web UI, no multimodal projector and no accelerator device. The Python client checks health and streams chat-completion events over loopback HTTP. Worker threads send status and text to the UI through a queue.

Current inference settings use three generation threads and four batch threads, a single parallel slot, batch size 128, microbatch 64, and q8_0 key/value caches. Context defaults to 768 tokens. These are source configuration facts, not performance recommendations for every compatible device.

Dictation runs ALSA recording and a local whisper-cli subprocess. Read-aloud synthesizes through the system espeak-ng library in a separate Python invocation and plays a WAV with ALSA. These paths do not call a hosted speech API.

The deployment system is separate from the app: shell bootstrap and four Python modules (SDL manager, shared backend, explicit headless CLI and installer_deps.py). The backend runs synchronously in a worker; the graphical manager owns confirmation, navigation and event presentation. This separation lets state transitions be tested without opening SDL. The local shell handles absent Python/curl before Python starts; the dependency helper handles capability checks and restricted APT setup, not GUI elevation.

Renderer

The handheld uses SDL2 KMSDRM with software rendering, not a browser, X11 application or Wayland client. The bootstrap exports SDL_VIDEODRIVER=kmsdrm and SDL_RENDER_DRIVER=software. Desktop mode leaves the desktop SDL environment unchanged. The app launcher also configures the handheld rendering environment.

SDL2_ttf provides text surfaces; the app has caches for text and background rendering. Chat messages are measured and wrapped against pixel widths at the 640 x 480 logical layout. Content viewports are clipped so scrolling or long text does not draw over fixed chrome. The intro is a finite sequence of prepared frames; the background afterwards is static, not a continuously decoded video.

The bootstrap SHA-256-validates regular and bold DejaVu Sans Mono fonts plus their existing license in MODULES/fonts/. The manager searches bundled font locations before the OS path; the app prefers bundled fonts in its data ROOT, with OS fonts as fallback. This removes a manual system-font prerequisite without bundling SDL or changing the graphics stack.

The manager maintains its own bounded text texture cache and redraws in a loop with a 1/30-second sleep between iterations; that is not a measured frame-rate claim. On KMSDRM systems where the Mali library exists at /usr/lib/aarch64-linux-gnu/libMali.so, it sets SDL's EGL/GL driver defaults to that library to avoid a known loader mismatch in this environment. This is a targeted compatibility path, not a replacement GPU stack.

The desktop preview imports the production app renderer and settings panel. Its conversation content is sample text. It intentionally avoids starting the device engine, recording audio, or writing device config/history. A preview capture is useful for layout work but is not proof of on-device inference or KMSDRM compatibility. Keep preview images distinct from real device captures.

Controller input

The tested controller emits raw SDL joystick button events. The app uses 0x603 for button-down handling and does not also dispatch 0x651 GameController button events. Processing both would risk duplicate actions, and the streams do not share every shoulder/D-Pad mapping.

Not every physical button has an app action. The app also handles joystick hats and polls analog axes, using the controller interface when available or the joystick interface otherwise. Its duplicate-press guard uses event timestamps rather than draw-frame timing, because events may queue during a slow render. The manager translates its raw buttons into its own small navigation vocabulary.

When porting to another image or controller, record the actual event stream before changing these numbers. Do not infer face-button meanings from labels used by another frontend. User-facing actions belong in the control reference, while this table describes the tested hardware protocol.

Downloads and trust

The public bootstrap is install227ai.sh on the existing v1.0.0 release. It downloads code rather than a frozen v1.0.0 app bundle. The bootstrap fetches four manager modules from repository main. If any module is absent, including the dependency helper, it downloads and validates the entire matching set before per-file publication. Complete stored sets remain cached. Runtime and model binaries use the release asset base, with Hugging Face as a model fallback. The default binary endpoint is releases/latest/download; the documented runtime release is v1.0.0.

For default online installs/updates, the core resolves GitHub main using api.github.com/repos/1Z99/project-ai-r36s/commits/main, validates the commit SHA, then fetches all staged app/assets/licenses/system files from that immutable revision. This is a consistent source snapshot, not a signed release or a fixed version baseline. API/rate-limit or source-fetch failures fail the check; cached source cannot silently prove freshness. Even a no-op needs internet. Local bundles compare local contents instead and are explicitly identified as local, not GitHub, in the UI.

Runtime and models have pinned SHA-256 values. The runtime sidecar must agree with the pin before the archive is accepted. Installed runtime reuse verifies actual files against its manifest and requires executable server/transcriber binaries. App Python files are compiled for syntax during staging, and system XML is parsed before publication. Raw source files are not individually hash-pinned or signed; an immutable commit URL is not independent authenticity verification.

The download backend uses bounded attempts and timeouts: 15 seconds to connect, a 30-second low-speed window at 1,024 bytes/second, and a 3,600-second maximum per payload attempt. Bootstrap modules use a shorter 120-second overall timeout. These are limits, not expected install durations.

Partial filenames are keyed by source URL, preventing one mirror's partial bytes from being appended to another mirror's response. Known hashes protect completed binary downloads. Raw-file resumes use an available strong ETag or Last-Modified validator with If-Range; without a validator they restart. A refused or out-of-range resume can also restart from zero. Progress comes from the final HTTP response, not a redirect's Content-Length.

Changing an environment override changes the trust source. PROJECT_AI_RAW_BASE controls manager/source URLs, PROJECT_AI_REL_BASE controls release assets and model mirrors, and PROJECT_AI_RUNTIME_LOCAL supplies a runtime archive with a mandatory adjacent sidecar matching the same pinned hash. file:// bases support local fixtures. A newer release asset cannot silently bypass a stale core's pins.

Safety model

Card discovery checks the real mount table, writable status and fixed mountpoints independently of EmulationStation's ROM layout. The UI requires an explicit card selection and confirmation. The CLI requires an explicit target and --yes for changes. Symlinked managed targets and unsafe target types are refused rather than followed.

Before an install/update, a free-space preflight starts from a conservative 650 MiB fresh budget and credits reusable runtime/model files and relevant retained downloads. When the installed runtime and both models verify, additional staging is budgeted at about 25 MiB. These are not exact install sizes; system packages need separate system-partition space. A per-card file lock prevents simultaneous mutations on the same destination. A second shared configuration lock serializes EmulationStation/theme work, including across different cards.

Content-based comparison returns up_to_date only if all managed source files, actual model/runtime hashes, owned ES/theme metadata, required executable permissions and config existence match expectations. A no-op skips app publication, not source checks, staging, cache/log activity or locks. ES statistics and unrelated metadata are preserved; harmless XML serialization changes do not create false updates. Missing/integrity/registration fixes report repair. Changed existing payload bytes report Updated/repaired files, since no release baseline distinguishes newer source from corruption.

Capability-first system setup

The shell checks installed Python 3.9+ and curl before invoking Python; absent tools may be installed, but existing broken/old Python fails without upgrade. Before manager Display startup, installer_deps.py checks manager SDL libraries and curl. After explicit install/update confirmation, the core calls its all scope for SDL/curl, the eSpeak library with usable English data, ALSA arecord/aplay/amixer and procps pkill. Working capabilities require no OS/package queries, APT calls or system changes. Desktop, help, dry-run and uninstall skip automatic setup; isolated non-card CLI fixtures do not install system dependencies.

Only missing capabilities cause OS/APT planning. Automatic setup requires Debian/Ubuntu-family aarch64, dpkg arm64, APT and root or noninteractive sudo -n. Unsupported/no-admin cases give an error and missing-package list without prompting for or storing passwords. Existing broken libraries are fatal, not a reason to reinstall firmware. This is a restricted helper, not a guarantee that every firmware or Linux distribution can install.

APT first simulates with --no-upgrade --no-remove --no-install-recommends. The helper audits and version-pins the full dependency closure and repeats simulation immediately before installation. It rejects upgrades/removals and protected graphics/firmware packages, including Mesa/EGL/GLES/GBM/DRM/Mali. Package indexes refresh only if initial simulation fails. Packages are outside the app transaction and SD budget, are shared OS dependencies, and remain after uninstall.

Payloads are staged before publication. File writes use temporary files and renames; existing replaced targets are moved into same-filesystem backup locations recorded by an in-memory journal. If a commit raises an exception, the backend attempts restoration in reverse order. Incomplete rollback reports its retained backup paths rather than deliberately deleting the remaining recovery copy.

Exception rollback is not crash-proof transactional storage. The journal is not a persistent recovery database and does not undo system packages. Sudden power loss, a killed process, filesystem failure or removal of a card can interrupt publication. Cancellation waits for running APT installation to finish before being honored and is deferred during commit, rollback and destructive uninstall. Do not power off during system setup or these phases.

Uninstall does not provide install-style restoration of deleted conversations. It removes owned app/data/cache paths on the selected card and only a matching 227 registration. It does not restore a whole historical EmulationStation config or remove another card's registration. Theme removal respects another remaining 227 registration or installed copy.

Manager files are outside the app backend's ownership. Bootstrap publication uses per-file atomic renames, not one atomic replacement of an entire module set. Complete module sets are cached; neither install nor Update / Repair performs manager self-update. Updating the bootstrap and four matching modules is a separate manual task. The backend may invoke the restricted dependency helper's root/sudo -n package operations, but the GUI is not elevated. There is no password prompt, service restart or automatic reboot.

Run the local suite

From the repository root, run the focused bootstrap and installer suites, including test_installer_deps.py. Dependency-helper tests mock host/package boundaries, not real APT installation. Review fixtures before extending destructive-operation coverage, and keep targets temporary rather than using a real card or live EmulationStation configuration. Local builds and preview

A checkout is already a source build: there is no application framework or web bundler to install. Python uses the standard library with native system SDL2/SDL2_ttf and bundled font assets. Desktop mode skips automatic dependency/font setup; supply working desktop libraries yourself. The aarch64 inference archive remains a binary dependency for real device inference.

Preview the interface on a computer

Run from the repository root
python3 dev/project_ai_preview.py --scene chat --skip-intro
python3 dev/project_ai_preview.py --scene settings --settings-page voice

The preview needs system SDL2/SDL2_ttf and the font assets in assets/. Supported scenes include chat, keyboard, models, history, waiting, speech, boot, mic and settings. --settings-page prompt --edit-prompt opens the system-prompt editor. --screenshot PATH writes a 640 x 480 PNG and exits; its parent directory must already exist. Settings in the preview are session-only, and its replies are demonstration text.

Exercise the graphical manager locally

Desktop manager, no handheld connection
sh install227ai.sh --desktop

From a checkout, the bootstrap uses the local installer/ modules without fetching them and automatically passes the checkout as --source when app/ exists. That means unpushed app/assets/system changes are exercised rather than published copies. Opening the UI is not a simulated card install: normal discovery still describes the actual fixed card mountpoints. Use the CLI with isolated paths for mutation tests. Local manager logs live in installer/.

Use an isolated CLI target

For local testing, the core accepts existing, writable absolute directories outside protected system locations. Prepare a temporary card directory, themes directory and a minimal XML configuration. The example below touches only its temporary test tree when preparing fixtures; the final command is read-only validation.

Local fixture and dry-run
mkdir -p /tmp/227-test/card /tmp/227-test/themes
printf '<systemList></systemList>\n' > /tmp/227-test/es_systems.cfg
sh install227ai.sh --cli --roms /tmp/227-test/card --action install --dry-run \
  --es-cfg /tmp/227-test/es_systems.cfg --themes /tmp/227-test/themes

Replacing --dry-run with --yes performs a real installation into that fixture, can download missing binaries, and consumes space. Dry-run only discovers and validates: it does not test transfers, staging or capacity. Never substitute a live configuration path by accident.

Make a fully local bundle

A self-contained manager can keep install227ai.sh and all four Python manager modules together, including installer_deps.py, with a bundle/ release tree beside them. The deployed manager retains tools/227-ai-manager/install.bootstrap; its non-.sh filename prevents EmulationStation from exposing the support folder as another tool. The updated public bootstrap publishes that file and the Tools shortcut before removing legacy internal install.sh. See migration instructions for existing users. Include complete app/, assets/, licenses/ and system/ directories, including regular/bold fonts and their existing license. Put the runtime archive and its pinned .sha256 sidecar plus both default model files at the bundle root. The UI/CLI recognize this bundle automatically, or you can pass --source PATH. Results explicitly compare this local bundle, not GitHub.

An incomplete local application bundle fails rather than mixing local source files with remote source files. Missing binaries can still trigger downloads, so a directory called bundle is not by itself an offline guarantee. For release assembly and redistribution, consult PUBLISHING.md and retain the third-party license notices.

Scope and omissions

This is a description of the current boundaries, not a schedule or promise of future releases. The app includes local text chat, short English dictation, selected-reply read-aloud, settings and saved conversations. The manager includes explicit card selection, install, preserving update/repair and destructive removal.

Not included: cloud synchronization, online search, automatic conversation backup, encrypted chat storage, an always-on microphone, continuous voice dialogue, automatic downloads of optional model profiles, manager self-update, or crash-proof recovery after a power cut. The current expression-helper bug means a working calculator should not be advertised.

Website navigation, search, screenshot slots and documentation are website features, not new handheld capabilities. Unfilled screenshot slots are placeholders, not evidence that an untested workflow has been verified. Proposals can be discussed in the issue tracker, with reproducible reports and clear separation between desired behavior and shipped behavior.
